## 实际问题与独立源码预期

旧 DLL 在列表项已有段落与缩进代码之间的 GAP 1 输入 `Z` 时，会整体序列化列表。根文档、有序列表、脚注、引用四种情况中，未编辑的实体 `&amp;` 被改写，缩进代码语法 8 改为围栏语法 3，编号分隔符可能变化。正文、重解析和 Undo 成立仍不足以证明无损编辑。

例如：

```markdown
- *A* &amp;

      code &amp;
```

独立预期为：

```markdown
- *A* &amp;

  Z

      code &amp;
```

四个预期来源均能独立解析并保持原代码语义与缩进语法。严格旧产品入口编译实际 0、运行指定负例实际 1，四处来源不符；原观察和日志保留在 `list-middle-gap-diagnostic-v1-proof.json`。该批旧列表已是松列表，块间来源保真仍需自己的输入边界计划。

## 同一事务中的实现

新私有来源计划根据 LIST_ITEM 的语义 child frontier 处理非首 GAP：

1. 验证新语义影子恰好增加一个段落，原孩子顺序与身份全部保留。
2. 使用 CST 块边界和 SourceLine 定位插入点。中间输入插在后续原块的物理行前；尾部输入使用前一块的物理行末。原块及源码间隙不重写。
3. 使用已有解析器确认的首行列表标记、任务标记、引用/脚注容器链与逻辑内容列生成续行前缀。部分 Tab 分开列，不把原代码缩进当成新段落缩进。
4. 只序列化新段落并补必要的空行，复用所在来源的行结束；处理原文件末尾没有换行的情况。
5. 对候选来源完整重解析，复用已有定义拼写保护和受影响列表祖先的派生属性计划。所有其他语义、属性、资源及定义仍需相等。
6. 只有证明成功后才发布候选；来源操作、位置映射、通知和 Undo/Redo 使用同一根事务。

现有首 GAP 来源计划继续处理列表标记行与已有载荷共享一行的输入。两条来源计划均在统一 Document 适配器中工作。完整候选和主工作区源码在此隔离验证期间保持不变。
