# XUI 高精度审计报告

审计日期：2026-09-05  
审计对象：`D:\GIT\xge` 当前主线中的 XUI 公共基础设施、控件实现、测试与视觉审计范例  
审计方式：静态调用链审计、全量单元测试、视觉审计、严格类型转换扫描、关键控件性能基线

## 1. 结论

XUI 已具备较完整的控件体系，近期完成的像素化布局、刚性 Stack、显式弹性 Flow、滚动内容隔离、编辑器增量处理和终端可视区渲染方向是正确的。当前主要风险不在“缺少更多控件”，而在公共契约还没有完全闭合：

1. 回调执行期间的对象生命周期没有统一保护，存在可构造的释放后使用风险。
2. 公开的状态变化事件没有从状态修改链路发出，导致依赖这些事件的弹层、终端和复合控件逻辑失效。
3. 渲染顺序、命中顺序、溢出策略和焦点有效性使用了不同的规则，界面显示与用户实际操作可能不一致。
4. 像素坐标迁移尚未完成，浮点值先写入整数矩形再调用像素吸附的模式仍大量存在。
5. TableView、RichEdit、MessageList、TreeView 和共享文字换行路径存在随文档规模或滚动深度放大的算法成本。
6. 可访问性、复合控件焦点模型、视觉自动验证和性能预算仍停留在框架或局部实现阶段。

建议先修复 P0/P1 公共基础设施问题，再开展控件级功能扩展。否则后续控件会继续复制不稳定的生命周期、状态事件、命中和坐标契约。

## 3. 严重级别

- **P0**：内存安全、对象生命周期或可导致不可预测崩溃的问题。
- **P1**：公共契约错误、高影响逻辑缺陷，或显示与交互不一致的问题。
- **P2**：明显的性能、可访问性、交互完整性和可维护性缺陷。
- **P3**：中长期质量、诊断能力和 API 清晰度改进。

## 4. P0 问题

### P0-1 回调生命周期屏障不完整

**现象**

XUI 只在部分事件派发和更新回调中增加 `iWidgetCallbackDepth`。多个公开回调会在深度为 0 时直接调用用户代码；用户代码若销毁 widget 或 context，调用者返回后仍继续使用旧指针。

**证据**

- 普通事件派发具备深度保护：`src/xui_input.c:2049-2130`。
- 更新回调具备深度保护：`src/xui_widget.c:5386-5417`。
- 键盘目标派发直接调用处理器：`src/xui_input.c:1648-1665`。
- `xuiInputKeyDownEx` 在目标回调后继续用之前保存的 `pKeyTarget` 执行冒泡：`src/xui_input.c:1735-1761`。
- 键盘冒泡从 `pTarget->pParent` 开始解引用：`src/xui_input.c:1668-1685`。
- `xuiWidgetDestroy` 在回调深度为 0 时可以立即冲刷延迟销毁：`src/xui_widget.c:3247-3274`。
- 热键回调直接执行，且回调返回后继续遍历热键数组：`src/xui_input.c:1598-1628`、`src/xui_input.c:1692-1717`。
- 缓存渲染回调后继续结束更新并清除 dirty：`src/xui_widget.c:6390-6410`。
- 布局 measure、arrange、prepare、complete 回调没有统一屏障：`src/xui_layout.c:42-107`、`src/xui_layout.c:316-333`、`src/xui_layout.c:414-447`。
- Tooltip resolver、自定义测量/绘制和可访问性 provider 也直接调用外部代码：`src/xui_widget.c:4921-5043`、`src/xui_widget.c:5466-5533`。
- 错误回调返回后仍写 context 字段：`src/xui_core.c:926-942`。

**影响**

- 键盘处理器销毁自身时可能触发释放后使用。
- 热键回调增删热键或销毁关联 widget 时可能破坏迭代。
- 布局、缓存绘制、Tooltip 和可访问性回调可以让调用栈中的 widget/context 失效。
- 问题具有输入时序依赖，普通单元测试难以稳定暴露。

**整改**

1. 建立统一的 `xuiCallbackEnter/Leave`，所有用户可注入回调必须通过同一入口。
2. 将 widget 销毁延迟到最外层 XUI 操作结束，而不只是单个事件回调结束。
3. 为 context 销毁建立明确契约：回调内延迟销毁，或公开禁止并在调试构建断言；推荐延迟销毁。
4. 回调前保存对象 generation/token，回调后先验证对象和操作是否仍有效，再继续访问。
5. 热键、监听器等可变集合使用快照或稳定句柄，不允许回调直接破坏当前迭代。

**必须补测**

- key target、key bubble、hotkey、layout、cache paint、Tooltip、accessibility 回调中分别销毁自身、父级和 context。
- 回调中移除另一个监听器、重新挂载 widget、关闭 popup。
- ASan/UBSan 构建和随机事件序列测试。

## 5. P1 问题

### P1-1 已公开的状态变化事件没有被发出

**现象**

API 定义了 `BOUNDS_CHANGED`、`VISIBLE_CHANGED`、`ENABLED_CHANGED`，事件掩码和多个控件处理器也已存在，但状态修改路径没有产生这些事件。

**证据**

- 事件定义：`xui.h:441-443`。
- 事件掩码映射：`src/xui_widget.c:27-63`、`src/xui_input.c:121-153`。
- Rect、Visible、Enabled setter 只修改字段和失效：`src/xui_widget.c:3446-3470`、`src/xui_widget.c:4142-4186`。
- 布局直接覆盖最终矩形：`src/xui_layout.c:414-447`。
- ComboBox 明确处理这些事件以同步弹层和状态：`src/xui_combobox.c:890-936`、`src/xui_combobox.c:1144-1160`。
- ColorPicker、DatePicker、Cascader、IconPicker、TextEdit、Terminal、MessageList、ListView、TableView、TreeView 中存在同类处理器。

**影响**

- owner 因布局移动或改变大小后，已打开 popup 不会可靠重新定位。
- owner 隐藏或禁用后，popup 可能继续存在。
- Terminal 的 bounds-change fit 路径不会自动执行。
- 事件 API 表面可用，实际订阅者永远收不到通知。

**整改**

将状态修改收口为事务：记录 old/new 值，在布局和属性更新完成后去重发出事件。事件应在几何稳定后发出，并定义同步、批量和重入语义。

### P1-2 隐藏、禁用、移除时静默清理输入状态

**现象**

widget 失效或离树时，公共输入层直接清空 hover、active、focus、capture、drag、press、hotkey 和队列引用，没有先向控件发送对应取消事件。

**证据**

- 集中清理逻辑：`src/xui_core.c:1129-1241`。
- Visible、Enabled、HitTestVisible、RemoveFromParent、Destroy 都会进入该清理：`src/xui_widget.c:4157`、`src/xui_widget.c:4180`、`src/xui_widget.c:4219`、`src/xui_widget.c:3390`、`src/xui_widget.c:3257-3269`。
- `xuiWidgetSetFocusable(false)` 直接清焦点：`src/xui_widget.c:4229-4243`。

**影响**

控件依赖 `POINTER_CAPTURE_LOST`、`DRAG_CANCEL`、pointer leave 或 blur 清理私有 pressed/drag/selection 状态。静默移除后再显示或重新挂载时，私有状态可能残留；IME、caret 和 accessibility focus 也可能不同步。

**整改**

统一 `cancel interactions for subtree`：按稳定顺序发送 drag cancel、capture lost、pointer leave、blur/IME stop，再移除公共引用。销毁路径必须使用受保护的事件事务。

### P1-3 焦点和视觉状态忽略祖先的有效状态

**证据**

- Tab 焦点收集只检查目标自身，不阻止遍历隐藏或禁用父级：`src/xui_input.c:749-826`。
- `xuiSetFocusWidget` 只检查目标自身：`src/xui_input.c:2349-2365`。
- `xuiWidgetGetInputState` 只读取自身 enabled：`src/xui_widget.c:4194-4205`。
- Popup owner 可用性和焦点恢复同样只检查 owner 自身：`src/xui_popup.c:268-296`、`src/xui_popup.c:600-640`。

**影响**

隐藏或禁用容器中的后代仍可能通过 Tab 或直接 API 获得焦点，并以 enabled 样式绘制；命中测试却会因祖先状态拒绝输入，形成三套不同状态。

**整改**

增加缓存或按需计算的 effective-visible、effective-enabled、effective-hit-test、effective-focusable，并让焦点、命中、样式、popup 和 accessibility 统一使用。

### P1-4 渲染顺序与命中顺序不一致

**证据**

- 渲染节点按 layer/z 全局稳定排序：`src/xui_widget.c:1468-1490`。
- 命中测试按兄弟插入顺序逆序遍历，不读取 layer/z：`src/xui_input.c:601-634`。
- `xuiWidgetSetLayer` 只更新字段和失效：`src/xui_widget.c:3800-3810`。

**影响**

两个控件重叠时，用户看到的最上层控件不一定收到点击。全局 layer 排序还可能让父级背景在子级之后绘制，缺少明确 stacking context。

**整改**

构建一次统一的 paint/hit stacking tree。每个 stacking context 内按 layer、z、稳定树序排序；命中按完全相反的最终绘制顺序执行。Popup、drag adorner、tooltip 使用明确的顶层 context。

### P1-5 `overflow: visible` 的绘制和命中语义冲突

**证据**

- 命中测试在点位不属于父级时直接返回，不继续检查子级：`src/xui_input.c:601-634`。
- 渲染只在 HIDDEN/CLIP 策略下裁剪子级，VISIBLE 子级可以画到父级之外：`src/xui_widget.c:1493-1524`。

**影响**

父级之外可见的子级像素无法交互。

**整改**

要么将 overflow-visible 子级纳入父级之外的 hit bounds，要么禁止普通树节点越界交互并要求弹层进入 overlay tree。API 需要给出单一、可测试的语义。

### P1-6 已挂载子级被当作独立根节点 arrange

**证据**

- 公共 `xuiWidgetArrange` 以 `parent=NULL` 同步布局：`src/xui_layout.c:494-520`。
- 父级相关坐标映射位于 `src/xui_layout.c:195-272`。
- 正确的子级入口是 `xuiLayoutArrangeChild`：`src/xui_layout.c:523-538`。
- ScrollView、Popup、IconPicker 对已挂载子级调用了根 arrange：`src/xui_scroll_view.c:122-131`、`src/xui_popup.c:441-481`、`src/xui_icon_picker.c:1190-1235`。

**影响**

子级可能在根坐标和父坐标之间反复同步，表现为 popup 或 cell editor 闪到左上角、位置抖动、尺寸多 1 至 2 px。

**整改**

区分 `ArrangeRoot` 和 `ArrangeChild`，内部 API 类型化，禁止已挂载节点走 root 入口；调试构建直接断言。

### P1-7 像素坐标迁移仍存在“先截断、后吸附”

**证据**

- `xui_rect_t` 已为整数，但字段仍命名为 `fX/fY/fW/fH`：`xui.h:1612-1619`。
- 正确的浮点边界转像素 helper：`src/xui_internal.h:607-619`。
- `xuiInternalSnapRect/Out/In` 接收的已经是整数 rect，且 Out/In 当前等价：`src/xui_internal.h:622-640`。
- 代码中约有 350 次 SnapRect 调用和至少 31 处明显的 `0.5f` 几何初始化。
- 典型位置：`src/xui_button.c:725-830`、`src/xui_date_picker.c:924-1245`、`src/xui_message_list.c:515-1265`、`src/xui_toggle.c:417-419`、`src/xui_tree_view.c:1407`。
- 全量扫描产生 1965 个 `-Wfloat-conversion` 告警。

**影响**

浮点值写入整数时先向零截断，后续 snap 已无法恢复原边界；负坐标、奇数宽度居中和缩放场景会出现方向相关的 1 px 偏差。Out/In 名称提供了并不存在的不同保证。

**整改**

1. 几何计算使用明确的 float-edge 临时类型，最终只允许一次 edge rounding。
2. XUI 布局、控件 box、clip、hit rect 全部使用 pixel 类型；路径、动画和变换保留 float。
3. 删除对整数 rect 无意义的 SnapRect，或改成接收 float edges。
4. 将 `fX/fY/fW/fH` 重命名为 `x/y/w/h`，利用编译器暴露遗漏迁移点。
5. 建立 DPI、负坐标、奇偶宽高和多层嵌套的像素黄金测试。

### P1-8 局部 damage 未覆盖布局连带移动

**证据**

- layout-change 失效只加入发生变化 widget 的当前 world rect：`src/xui_widget.c:2210-2214`。
- `__xuiLayoutApply` 直接覆盖所有计算矩形，没有记录 old/new world bounds：`src/xui_layout.c:414-447`。
- `xuiRender` 在调用方不提供 rect 时依赖 context damage：`src/xui_core.c:3015-3018`。
- 当前所有示例均显式传入 full rect，实际绕过了局部 damage 风险。

**影响**

子项 A 尺寸变化导致兄弟 B 移动时，B 的旧位置和新位置不一定进入 damage，局部重绘可能残影或漏画。

**整改**

布局事务开始前保留旧 world bounds，apply 后计算新 bounds，将 old ∪ new 纳入 damage；父级 clip、阴影和溢出扩展也要计入 visual bounds。

### P1-9 DPI 更新未使布局和渲染缓存失效

**证据**

- `xuiSetVirtualDpi` 只修改 scale 并请求全屏 damage：`src/xui_core.c:1692-1708`。
- SVG 栅格尺寸依赖 DPI：`src/xui_icon.c:454-463`。
- 没有统一增加 layout、text、icon 和 widget cache generation。

**影响**

SELF cache 或图标缓存可能继续显示旧 DPI 结果；全屏重绘并不等价于重建缓存。

**整改**

引入 `dpiGeneration`，DPI 改变时使 layout metrics、text layout、icon raster、widget cache 和 popup placement 全部失效，并在新 scale 下重新量化像素边界。

### P1-10 Drag/Drop 回调重入会让目标和传输状态失效

**证据**

- target transition 先发 LEAVE，回调后无条件使用之前计算的新 target：`src/xui_drag_drop.c:342-375`。
- drag dispatch 回调返回后继续写 context negotiation 状态：`src/xui_drag_drop.c:253-286`。
- drop 路径同样在回调后继续使用 context：`src/xui_drag_drop.c:378-397`。

**影响**

LEAVE 回调中取消拖放、销毁新 target 或销毁 context 后，调用方仍可能写入失效状态或向失效 target 派发事件。

**整改**

Drag session 使用稳定 ID/generation；每次用户回调后重新验证 session、context 和 target，必要时重新 hit test。生命周期修复应与 P0-1 使用同一套回调屏障。

### P1-11 TableView 的 merge owner 查询破坏虚拟化复杂度

**证据**

- `__xuiTableViewMergeOwner` 从 `(0,0)` 扫描到目标行列：`src/xui_table_view.c:651-675`。
- 即使 `onMerge == NULL` 也没有快速返回。
- 每个可见 cell 绘制前都调用 owner 查询：`src/xui_table_view.c:1938-1946`。
- hit test 和 ensure-visible 也调用同一逻辑：`src/xui_table_view.c:1181-1197`、`src/xui_table_view.c:1256-1291`。
- 首个可见行、row top、content height 和 row hit 也包含线性扫描：`src/xui_table_view.c:498-524`、`src/xui_table_view.c:565-582`、`src/xui_table_view.c:1921-1935`。

**影响**

滚动到深处后，每个可见 cell 都会叠加与行号相关的 adapter 回调。即使没有合并单元格，复杂度也会随数据深度增长；adapter 稍昂贵即会明显卡顿。

**整改**

先增加 `onMerge == NULL` 的 O(1) 快速路径。随后使用行高前缀索引或 Fenwick tree、merge owner 稀疏索引和数据 generation 缓存，使可见区定位接近 O(log N + visible cells)。

## 6. P2 问题

### P2-1 复合控件产生重复或无效 Tab stop

- TableGrid 根节点可聚焦且是 tab stop，内部 TableView 同样可聚焦：`src/xui_table_grid.c:1280-1345`、`src/xui_table_view.c:2210-2211`。
- PropertyGrid 根节点可聚焦，同时包含 TableGrid/TableView：`src/xui_property_grid.c:1170-1261`。
- PropertyGrid 外层主要处理 pointer，没有与这个额外焦点站点匹配的键盘行为。

应建立 composite focus owner/roving tabindex。一个复合控件对外只暴露一个 Tab stop，内部方向键在 active descendant 间移动。

### P2-2 Modal popup 可以没有焦点入口，无法构成焦点陷阱

- Popup 建立 focus scope，但自身默认不是 tab stop：`src/xui_popup.c:976-979`。
- scope 从当前 focus 祖先推导，否则退回 root tree：`src/xui_input.c:758-771`。
- Tab 即使没有移动焦点也被标记 consumed：`src/xui_input.c:1768-1780`。

`modal + focus none` 时焦点可以留在背景，Tab 仍在根树工作。Modal 应强制初始焦点、使背景 inert、循环 Tab，并可靠恢复 owner 或最近可用祖先。

### P2-3 部分可交互控件缺少键盘等价操作

- Chart 设置 focusable/tabstop，但主要只有 pointer 交互：`src/xui_chart.c:2084-2092`。
- Breadcrumb 主要为鼠标命中和点击：`src/xui_breadcrumb.c:473-518`、`src/xui_breadcrumb.c:603-604`。

应为可聚焦控件定义最小键盘契约：方向导航、Enter/Space 激活、Esc 取消、Home/End、可见 focus ring。若没有键盘行为，就不应占用 Tab stop。

### P2-4 MessageList 精确文字命中为 O(n²)，且不识别 grapheme cluster

- 文字命中逐 UTF-8 codepoint 枚举，每个 offset 都重新分配/复制前缀并从行首测量：`src/xui_message_list.c:664-747`。
- 共享文字布局已经能提供 shaping cluster：`src/xui_text.c:131-164`。

长消息拖动选区会产生大量小分配和重复测量；emoji、组合音标和 ZWJ 序列可能落在非法 caret 位置。应从共享 text layout 暴露 cluster hit-test/caret API，MessageList 不再自行切 UTF-8。

### P2-5 MessageList 对完整消息树重复布局和线性命中

- 每次布局遍历全部节点：`src/xui_message_list.c:480-569`。
- 每个节点会创建/销毁 text layout：`src/xui_message_list.c:451-470`。
- 命中线性扫描所有节点：`src/xui_message_list.c:597-616`。
- render/getter 路径可能重复触发布局：`src/xui_message_list.c:1193`、`src/xui_message_list.c:1620-1676`。

滚动内容已经不会反向影响外层布局，但控件内部仍需要 width/version 缓存、持久 text layout、消息高度前缀索引、二分可视范围和增量失效。

### P2-6 RichEdit 大文档首帧和全局变化成本过高

- 10000 段、约 970 KiB 文档首帧约 396.67 ms。
- 全量遍历顶层 block 布局：`src/xui_rich_edit.c:1169-1210`。
- hit test 为得到文档和行范围扫描大量 fragment：`src/xui_rich_edit.c:1397-1479`。
- link/atomic hit 为线性扫描：`src/xui_rich_edit.c:1482-1524`。
- render 两次遍历全部 fragment 后才做可见性剔除：`src/xui_rich_edit.c:1823-1923`。
- inline widget arrange 也遍历全部 fragment：`src/xui_rich_edit.c:1944-1983`。

局部编辑已经较快，但首帧、resize、字体变化和全局样式变化会冻结。应引入段落高度索引、可见 fragment 二分、惰性段落布局、稳定估算高度和可视区 inline widget materialization。

### P2-7 共享文字换行扫描复杂度和 Unicode 断行能力不足

- range measure 和 next-cluster 会从 shape 数组起点重复扫描：`src/xui_text.c:131-164`。
- paragraph wrap 对每个 cluster 调用这些函数：`src/xui_text.c:280-355`。
- break opportunity 主要只识别 ASCII 空格和 tab：`src/xui_text.c:181-207`。

应预计算 cluster prefix advances 并维护游标索引，把换行收敛到线性；断行规则应接入 Unicode Line Breaking Algorithm，至少正确覆盖 CJK 标点、不可断空格、emoji 和双向文字边界。

### P2-8 TreeView 层次索引重建为 O(N²)

- ID lookup 和 visible lookup 为线性：`src/xui_tree_view.c:346-373`。
- 展开节点时扫描全表找直接子项：`src/xui_tree_view.c:504-531`。
- 重算 children 时每个节点再次线性查找：`src/xui_tree_view.c:534-550`。

行绘制已有可视区思想，但数据索引会限制大树。应建立 ID hash map、parent-to-children adjacency 和可见子树 splice，避免每次展开重建全量可见表。

### P2-9 Terminal 吞吐可用，但历史存储内存放大明显

- 4 MiB 输入解析约 207.10 ms，约 19.31 MiB/s。
- 20000 行历史时常驻约 51064 KiB，约为输入量 12 倍。
- cell/history/view/cache 等结构并存：`src/xui_terminal.c:80-131`、`src/xui_terminal.c:908-1091`。
- 绘制已经按 dirty/visible row 工作：`src/xui_terminal.c:5421-5606`。

终端当前架构并非整体失效，TUI、历史和可视区增量方向正确。下一步应压缩历史行为 run/attribute run，只为 live screen 和 alternate screen 保留完整 cell grid，并建立增量 reflow 索引。性能测试需要加入帧时间和内存硬预算，而不只是最低吞吐。

### P2-10 可访问性仍是局部骨架

- 公开 role 主要偏文档节点，缺少常规按钮、输入、列表、表格、菜单、对话框等角色：`xui.h:488-501`。
- 当前主要由 RichEdit 安装 provider：`src/xui_rich_edit.c:3107-3108`。
- 焦点变化链路没有形成统一 accessibility focus 通知。

需要语义树、标准 role/state/action/value/range/text pattern、accessible name/help、active descendant、focus/live-region 通知，以及虚拟列表的按需语义节点。

### P2-11 公开缓存策略会静默降级为另一种策略

- API 暴露 TILED、DISPLAY_LIST、AUTO：`xui.h:337-342`。
- effective policy 将 TILED 映射到 SUBTREE、DISPLAY_LIST 映射到 SELF：`src/xui_core.c:2735-2746`、`src/xui_widget.c:1392-1399`。

这会让调用者误判性能和失效语义。未实现的策略应明确返回 unsupported，或通过 capability 查询后才能启用，不能静默改变含义。

### P2-12 视觉审计覆盖广度看似足够，验证深度不足

当前 audit 场景多为占位标签或静态触发态，没有自动执行 hover、active、focus、disabled、popup open、拖动、滚动和重叠命中。应把视觉测试改为输入脚本加像素/结构断言，并覆盖：

- DPI 1.0、1.25、1.5、2.0。
- 奇偶宽高、负偏移、多层嵌套和非零 viewport origin。
- 默认、hover、pressed、focus、disabled、selected、error。
- popup 首次打开、owner 移动、边缘翻转、关闭和焦点恢复。
- layer/z 重叠、overflow、clip、局部 damage。
- 长文本、CJK、emoji、RTL、超长单词。

## 7. P3 问题

### P3-1 同一帧存在重复布局遍历

- `xuiHitTest` 每次调用布局：`src/xui_input.c:2178-2200`。
- `xuiRenderPrepare` 调用布局：`src/xui_widget.c:6531`。
- `xuiBuildRenderTree` 再次调用布局：`src/xui_widget.c:6637`。

稳定布局时虽然可能快速返回，但仍有遍历和统计成本。建议建立 frame/layout generation，保证一个 generation 只提交一次布局；输入引发新 dirty 时显式推进 generation。

### P3-2 像素类型与历史浮点命名混用

整数 rect 使用 `fX/fY/fW/fH`，几何 API 中又同时存在真正的 float path/transform/measure。命名会持续诱发错误转换。

建议拆分：

- `xui_point_px_t`、`xui_size_px_t`、`xui_rect_px_t`：最终布局、clip、hit、damage。
- `xui_point_f_t`、`xui_rect_f_t`：动画、路径、变换和测量中间结果。
- float 到 pixel 只能通过命名明确的 edge-rounding API。

## 8. 控件族启发式改进

### 基础交互控件

- Button、Toggle、CheckBox、Radio、Slider、SpinBox 统一 pointer capture、键盘激活、repeat、cancel、focus ring 和 disabled 语义。
- 点击手势应以 press target、capture、release-inside 和取消原因组成统一 state machine，避免每个控件自行拼装。
- 命中区域与可见像素分离，允许 3 px splitter 拥有更宽的抓取区域，但 drag adorner 仍严格等于 3 px。

### 弹层与选择器

- ComboBox、DatePicker、ColorPicker、IconPicker、Cascader 共用 owner tracking、placement、focus scope、outside click、Esc、滚动祖先变化和窗口边界翻转服务。
- 弹层位置只接受 world pixel rect，不允许控件自行混用 root/local/world 坐标。
- Popup 应提供 placement diagnostics，能够输出 owner rect、anchor、chosen side、clip viewport 和最终 rect。

### 列表、表格和树

- 统一 virtual collection 接口：稳定 item ID、count/version、估算高度、精确高度、可见范围、selection、active descendant。
- TableView/TableGrid/PropertyGrid 共享 cell editor host，明确 editor 是 overlay，不参与表格行列布局。
- 大数据控件应将 adapter 回调次数纳入性能测试，防止“绘制行数少但数据回调巨大”。

### 文本与编辑器

- CodeEdit 已证明可视区和增量索引有效，RichEdit、MessageList 和 TextEdit 应复用同一层 text layout/hit-test/selection 服务。
- 统一 grapheme、word、line、paragraph 边界；IME composition、caret、selection、clipboard、drag text 和 accessibility text range 使用相同索引契约。
- Word Wrap 应依赖共享 cluster/prefix 数据，而不是各控件重新测量 UTF-8 前缀。
- 内嵌 widget 必须有独立 materialization 生命周期，离开可视区后不继续 arrange/render，但文档模型保持稳定占位。

### Window、DockPanel、SplitLayout

- 拖动和 resize 使用统一 drag session、pointer capture、preview overlay 和 commit/cancel 事务。
- preview rect 和最终 commit 必须来自同一个纯函数，避免虚影与松手位置使用两套计算。
- Dock guide、window outline、splitter adorner 进入专用 interaction overlay layer，不复用 tooltip/popup 语义。
- 建立多窗口、窗口外拖动、capture lost、DPI 切换和非零 viewport origin 自动测试。

### Terminal

- 继续保持 parser/model/view/render 分层，不把历史缓冲区退化为当前可见屏幕。
- 增加查找结果索引、鼠标模式协商、selection 与 TUI mouse ownership 的可见状态。
- 对 micro/vim 类程序建立固定回归：alternate screen、resize/reflow、wide glyph、combining mark、SGR、bracketed paste、mouse 1000/1002/1003/1006。

## 9. XUI 系统级演进

### 9.1 统一操作事务

输入、布局、属性更新、popup 和 drag/drop 都应运行在 `XUI operation` 中。事务负责：

1. 延迟对象销毁。
2. 合并状态变化事件。
3. 提交布局。
4. 计算 old/new visual damage。
5. 更新 hover/focus/capture/IME/accessibility。
6. 最后冲刷销毁队列。

这会同时解决当前多处“回调之后对象失效”和“状态改变后通知缺失”。

### 9.2 建立统一的场景树契约

布局树、绘制树、命中树、语义树可以有不同数据结构，但必须由同一组有效状态和 stacking context 派生。当前最危险的是每条链路各自解释 visible、enabled、layer、overflow 和 popup。

### 9.3 完成像素化边界

布局最终输出、world transform 后的控件 box、clip、hit、damage 均为整数像素；动画和路径可以保持浮点。任何浮点结果只能在进入最终 box 边界时量化一次。对 1 px/2 px 线条使用 edge 坐标，而不是“中心点加 0.5”写入整数矩形。

### 9.4 把文字服务提升为公共基础设施

共享服务应直接提供：shape clusters、prefix advances、line break、bidi runs、grapheme/word boundaries、point-to-caret、caret-to-rect、range rects 和可见行索引。编辑器和消息控件不再自行实现 UTF-8 前缀测量。

### 9.5 建立性能契约

每个虚拟控件至少定义以下预算：

- 首帧时间。
- 稳态滚动 P50/P95。
- 单次输入延迟。
- adapter/provider 回调次数。
- 文档规模与内存放大系数。
- resize 和 DPI 切换时间。

性能测试应在 CI 中使用宽松但明确的失败阈值，避免只打印数字。

### 9.6 增加调试和可观测能力

建议增加可切换的 XUI Inspector overlay：

- layout requested/actual rect、world rect、clip 和 visual bounds。
- stacking context、layer/z 和最终 paint/hit 序号。
- focus、hover、capture、drag owner、popup owner。
- dirty flags、damage rect、cache generation、DPI generation。
- measure/arrange/render 次数和耗时。

这类信息能直接定位“画在这里却点到别处”“旧区域未刷新”“弹层闪到左上角”等问题。

## 10. 建议实施顺序

### 阶段 A：先消除不确定行为

1. P0-1 统一回调生命周期和 context 销毁契约。
2. P1-10 Drag/Drop 重入保护。
3. P1-1 状态变化事件事务。
4. P1-2/P1-3 统一取消事件和 effective state。

### 阶段 B：统一用户看到和点到的世界

1. P1-4 stacking context 与反向命中。
2. P1-5 overflow 语义。
3. P1-6 root/child arrange 分离。
4. P1-7/P1-8/P1-9 像素、damage 和 DPI generation。

### 阶段 C：解决规模化性能

1. TableView 无 merge 快速路径和索引。
2. 共享文字 cluster/prefix/line-break 服务。
3. RichEdit 可见区惰性布局。
4. MessageList 持久布局与高度索引。
5. TreeView 层次索引。
6. Terminal 紧凑历史存储。

### 阶段 D：补齐产品级交互

1. 复合焦点、modal focus trap 和键盘等价操作。
2. 常规控件 accessibility 语义。
3. 自动视觉交互矩阵。
4. Inspector、断言和性能 CI 门槛。

## 11. 验收门槛

公共基础设施整改完成后，至少满足：

1. 所有公开用户回调都通过统一生命周期屏障，回调中销毁自身不崩溃。
2. Rect/Visible/Enabled 每次有效变化恰好产生一次稳定事件。
3. 隐藏、禁用、移除和销毁能完整取消 capture、drag、focus、IME 和 accessibility 状态。
4. 任意 layer/z 重叠场景中，最上层可见控件总是最先命中。
5. DPI 1.0/1.25/1.5/2.0 下，1 px 和 2 px 边框在四边宽度一致。
6. 使用 context damage 的局部渲染通过移动、resize、scroll、popup 和阴影残影测试。
7. TableView 深滚动时 adapter 调用量只与可见单元格和对数索引有关。
8. RichEdit 10000 段首帧不产生数百毫秒 UI 阻塞，滚动不遍历全量 fragment。
9. MessageList 长消息 hit-test 只落在合法 grapheme 边界，拖选不发生 O(n²) 分配。
10. 键盘、鼠标、触摸、IME 和 accessibility 对 effective state 使用同一判定。

## 12. 审计边界

本轮结论基于当前主线静态实现、已有测试和本机性能运行。视觉审计尚未包含真实 GPU 像素差异、跨平台窗口系统事件和屏幕阅读器实测，因此 macOS/Linux 后端、真实高 DPI 多显示器迁移和辅助技术兼容性仍需要专项验证。
