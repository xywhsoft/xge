## 问题与独立证据

旧 front matter 采集器只按 LF 分行。纯 CR 和部分 LF/CRLF/CR 混合输入被解析为普通 Markdown，而非开头元数据块。实际 DLL 的独立 108 场景探针有 76 个识别失败；原字节及失败日志保留。换行来源修复后的实际 DLL 执行最终 v5 黄金驱动仍退出 1，确认这是另一个问题。

只修复全文识别还不够：删除 opening marker 后的空格，或将空格替换为 LF，能够把原来的 thematic break 激活为 front matter。关闭行可能位于增量窗口之外；依赖复用也可能把原来的 Setext 块遮蔽，连同其中的关闭行一起隐藏。候选 v1/v2/v3 的差分失败和 v3 调试记录保留，不把全文与增量共享的错误当作通过。

## 候选实现

全文采集与依赖解析共享一个内部 front matter 范围识别函数：同时识别 LF、CRLF、CR，支持两种关闭标记及关闭行位于 EOF，正文和来源范围保留原字节。扫描检查取消状态；非 opening prefix 的普通输入先执行常量长度检查。

第一块形成 opening prefix 时，单块增量窗口必须交给拥有完整上下文的依赖路径或全文解析。依赖屏蔽前在真实输入上识别范围，范围内旧块不允许被省略；范围外仍按已有证明复用。发布继续使用唯一 Document 的树、源码、定义及历史，不新增公共 API 或旧接口包装。
