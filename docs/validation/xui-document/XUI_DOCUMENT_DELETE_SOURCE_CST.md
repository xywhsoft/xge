## 真实问题与修复

前候选删除 `> a[^drop] end` 中最后一个脚注引用已经可以成功，但会将整个引用块重新序列化，产生多余的空引用行。通用命令成功并不代表未操作源码保真。

当前修复复用同一 Document 的解析器确认行内语法、源码存储、语义投影、事务和历史。识别单次删除 Paragraph/Heading 内一个无子节点的操作，使用原始内容范围找唯一行内归属；目标、标题字段不会被误认成外层对象。只有完全由被删除内容占用的外层包装一并删除。纯 Text/HTML 的自身原始范围也可构成候选。没有引入第二个 Markdown 解析器、文档模型或旧 API 包装。

源码补丁先在私有事务中完整重解析，证明普通正文及保留脚注的完整语义，并检查受保护定义的原字节，之后才能发布。仅当正在编辑已经确认的脚注正文时，该正文可变，标签前缀与其他定义仍受保护。

段首删除可能使剩余的一个字面空格变为 Markdown 缩进并被解析器吞掉。直接删除不能证明语义时，只有原树下一项为 Text、其原范围紧接被删除范围、原字节与语义首字节均为 ASCII 空格的情形，才尝试将这个相邻边界字节改为 `&#32;`。第二次完整解析仍须证明全部语义和定义保护。例如删除 `> &amp; end` 的首个实体节点后得到 `> &#32;end`，保留显示空格，并保留原引用前缀、行结束和其余字节。这里的边界空格已发生语法意义变化，不能宣称它的原字节不变。
