## 统一来源计划中的代码边界写入

`xuiDocumentTxnReplaceText` 和 `xuiDocumentTxnReplaceRange` 都通过同一 Document/CST 来源计划处理代码文本。解析器确认的代码范围决定开闭反引号和原有填充空格；期望完整逻辑代码字串决定定界符是否冲突以及是否需要边界填充。非冲突的旧宽度保留，冲突时采用大于最长内部反引号串的宽度。

首尾反引号、两端空格和全空格文字分别处理：必要时添加填充，原有可保留填充不被重写，变为全空格时移除旧的被解析器忽略的填充。删除同样扫描替换后的完整字串，能够发现两个未编辑反引号串在删除处合并形成的新冲突。

来源补丁按旧坐标降序写入引用使用后缀、代码闭标记、选中内容和代码开标记。选区之外的代码负载、实体、链接目标、标题和定义保留原字节。影子文档完整重解析和语义核对后，才通过统一事务发布为一条历史；扫描和分配沿用现有取消与错误传播。

## HTML 缓冲区的分配与清理

HTML 导出仍将相同属性的连续 Text 输出为一个格式段，不修改 Document 节点。缓冲区预留与写入分开；预留先验证长度加法，按几何级数增长，成功分配并复制旧内容后释放旧缓冲区。失败时旧缓冲区仍由导出上下文持有，最终导出边界释放它，并保持调用方输出指针为空、输出长度为零。

分配失败驱动直接编译生产导出器，替换其 libc 分配边界并重命名测试入口，不复制一个测试专用导出实现。它是静态内核故障验证，不声明为 Windows DLL 的故障注入。45 个静态驱动接入 Windows/Linux 入口，26 个正常 DLL 驱动继续核对真实公开 API 的成功路径。

显式分配/复制会在增长时同时持有旧、新缓冲区；几何增长保留线性总复制量，但不宣称已完成大文档导出峰值或 P95 验收。

## 原失败与尚未完成的正确性问题

GFM/HTML 父批的正常 DLL 64 条、Core 80 条、Windows 270 条和 Linux 224 条已实际退出 0。但 HTML 静态分析在 `realloc` 失败分支报告泄漏，串行控制器实际退出 1，不能说父批全部通过。仅拆出预留函数的 v4 仍复现诊断，v5 改为显式分配/复制/释放后通过；没有关闭诊断或降低警告门槛。原轨迹包含“成功移动分配”之后又走空指针分支，因此原轨迹本身不足以证明真实运行泄漏；新的故障注入独立核对实际清理行为。静态分析的能力边界参见 [GCC 官方说明](https://gcc.gnu.org/onlinedocs/gcc/Static-Analyzer-Options.html)。

最初故障驱动只有未使用的黄金数组导致编译失败；修正为实际核对完整逻辑文字后通过，产品没有因此改变。原输入、日志与诊断保留。

原组合矩阵另发现：链接定义位于脚注内部时，加载后的代码 Text 没有 LINK 标记，失败发生在编辑 API 调用之前。当前解析器在 `md_end_current_block` 中禁止脚注内部消费引用定义，而且脚注正文在全局引用表构建后才解析。这是原批次确认的加载/引用投影缺口。后续脚注候选已在相同正文块语法完成预采集/重放、顺序、来源/CST 和编辑专项，仍需完整门禁及合入后正式验收。

当前代码边界矩阵将引用定义保留在脚注外，专门验证脚注正文里的编辑。这一限定范围不关闭脚注内定义要求，也不声明所有代码语法、完整 CST 或所有命令已经完成。
